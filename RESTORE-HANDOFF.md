# Рестор на телефоне: передача дел

Цель: **приложение восстанавливает прошивку гостя целиком на телефоне**.
Пользователь сам достаёт файлы (IPSW, `ticket.shsh2`, ключ SEP, SEP ROM) и кладёт
их в папку приложения — всё остальное делает приложение, без компьютера.

Этот файл — рабочая записка: что сделано, чем доказано, что дальше и где грабли.
Обновлять по ходу. Разбор находок по эмулятору — [`RESTORE-FINDINGS.md`](RESTORE-FINDINGS.md),
инструкция для человека — [`RESTORE.md`](RESTORE.md).

## Что делать дальше, по порядку

1. ~~**Прошивка SEP**~~ — сделано, `SEPFirmware.swift`. Выяснено на живых файлах:
   payload расшифровывается AES-256-CBC **без набивки** (ключ 32 байта, IV 16,
   пользователь берёт их с The Apple Wiki одной строкой в 96 шестнадцатеричных
   цифр); заново собирается как `IM4P` типа **`rsep`**, версии **`none`**, **без**
   свойств исходного IM4P (они описывали шифрование), и заворачивается в
   `IMG4 { "IMG4", IM4P, [0] IM4M }`. Стенд сверки: `<scratch>/septest`.
2. ~~**Чтение IPSW**~~ — сделано, `IPSW.swift`, стенд `<scratch>/ipswtest`.
   Проверено на настоящем архиве 6,4 ГБ: оглавление читается мгновенно (110
   файлов, zip64), `DeviceTree` и RAM-диск (117 440 539 байт за 0,3 с)
   распаковываются **побайтно так же, как `unzip`**. Образ системы лежит в
   архиве **без сжатия**: `rangeOfStored` даёт смещение 1222913566 и длину
   4922702471, сверено с `unzip -p` по SHA256 первых 4 КБ. Сам образ начинается
   с `bvxn` — это **lzfse**, а не сырой APFS: при ресторе его надо гнать в ASR
   как есть, не разбирая.
3. ~~**Протокол рестора**~~ — написан, `RestoreClient.swift`; разбор протокола
   ниже отдельным разделом. Проверено на настоящей прошивке: персонализация
   компонентов (`KernelCache`, `DeviceTree`, `LLB`, `iBoot`, `SEP`, `RestoreSEP`)
   **совпадает с `img4lib` байт в байт** — стенд `<scratch>/comptest`
   (`IMG4.swift` + `IPSW.swift` + заглушка `L()`), сверка с
   `img4 -i <im4p> -M root_ticket.der -o ref.img4`. Список прошивок для NOR,
   выбранный по манифесту iOS 16, — ровно `all_flash`: `AppleLogo`,
   `BatteryCharging0/1`, `BatteryFull`, `BatteryLow0/1`, `BatteryPlugin`,
   `DeviceTree`, `LLB`, `LowPowerWallet0/1`, `RecoveryMode`,
   `WCHFirmwareUpdater`, `iBoot` (14 штук).

   **Не проверено вживую**: сам обмен с гостем. Следующий шаг — прогон на iOS 14
   (`~/inferno-ios/ios14ab`), где RAM-диск доходит до ожидания хоста.
4. **Экран мастера**: выбрать IPSW и `ticket.shsh2` в Файлах, ввести ключ SEP,
   показать ход. Сейчас есть только «Параметры → Восстановление» с проверкой
   связи.
5. **Патчи файловой системы**. `InfernoFSPatcher` меняет байты в dyld cache **на
   месте** (размер не меняется) — это можно сделать разбором APFS только на
   чтение. Отключение служб в `launchd.plist` и бутстрап требуют настоящей
   записи: идея — подменить на месте бинарник ненужного демона нашим агентом
   (кэши подписей эмулятор всё равно не проверяет) и дальше работать изнутри
   гостя. Не проверено.
6. **Бутстрап**: rootful Procursus (для 16 — `static.palera.in/bootstrap-1900.tar.zst`),
   дальше `prep_bootstrap.sh` и Sileo/Zebra из `strap.palera.in`.

## Протокол рестора: что именно шлётся

Разобрано по `~/inferno-ios/tools/idevicerestore/src/{restore.c,asr.c}` и
`~/inferno-ios/tools/libimobiledevice/src/restore.c`. Ниже — то, что нужно
повторить, без обвязки.

### Канал `restored` (порт 62078)

Кадр: плист **в XML**, за четырёхбайтовой длиной big-endian. Первым делом
`{Request: QueryType, Label: …}`; в ответ `Type = com.apple.mobile.restored` и
`RestoreProtocolVersion`.

Старт — `{Request: "StartRestore", RestoreOptions: <опции>,
RestoreProtocolVersion: <версия из QueryType>, Label: …}`. **Ответа на него нет**,
дальше идёт поток сообщений от гостя.

Опции для устройства (не macOS), ровно как у `idevicerestore`:
`AutoBootDelay=0`, `BootImageType="User"`, `DFUFileType="RELEASE"`,
`DataImage=false`, `FirmwareDirectory="."`, `FlashNOR=true`,
`KernelCacheType="Release"`, `NORImageType="production"`,
`RestoreBundlePath="/tmp/Per2.tmp"`, `SystemImageType="User"`,
`UpdateBaseband=true`, `InstallDiags=false`, `PersonalizedDuringPreflight=true`,
`RootToInstall=false`, `CreateFilesystemPartitions=true`, `SystemImage=true`,
`UUID=<произвольный GUID>`, `SystemPartitionPadding` (из
`Info/SystemPartitionPadding` манифеста, иначе таблица по умолчанию), плюс
`SupportedDataTypes` и `SupportedMessageTypes` — два словаря «имя → bool»,
скопированные из Apple Configurator. Булево значение в них **не значит «умею»**:
у `idevicerestore` `NORData`, `RootTicket`, `KernelCache`, `SystemImageData`
стоят в `false`, и всё равно приходят и обрабатываются. Значит, таблицы надо
копировать дословно, не «чинить».

Сообщения различаются по `MsgType`: `DataRequestMsg` (главное),
`ProgressMsg`, `StatusMsg`, `CheckpointMsg`, `PreviousRestoreLogMsg`,
`BBUpdateStatusMsg`, `CrashLog`. Конец — `StatusMsg` с `Status = 0`, на него
отвечают `{MsgType: "ReceivedFinalStatusMsg"}` и закрываются.

**Куда отвечать.** Если в запросе есть `DataPort` — ответ идёт **новым
соединением** на этот порт (так с iOS 17), если нет — в тот же канал `restored`.
Для iOS 14 `DataPort` не приходит.

### Ответы на `DataRequestMsg` по `DataType`

| `DataType` | Ответ |
|---|---|
| `RootTicket` | `{RootTicketData: <наш IM4M>}` |
| `KernelCache` | `{KernelCacheFile: <IMG4 из IPSW + тикет>}` |
| `DeviceTree` | `{DeviceTreeFile: …}` |
| `SystemImageRootHash` | компонент `SystemVolume` в ключе `SystemImageRootHashFile` |
| `SystemImageCanonicalMetadata` | компонент `Ap,SystemVolumeCanonicalMetadata` в ключе `SystemImageCanonicalMetadataFile` |
| `BuildIdentityDict` | `{BuildIdentityDict: <identity>, Variant: <Arguments/Variant> или "Erase"}` |
| `ReceiptManifest` | `{ReceiptManifest: <identity/Manifest>}` |
| `FDRTrustData` | **пустой словарь** — так делает и iTunes |
| `NORData` | см. ниже |
| `PersonalizedBootObjectV3`, `SourceBootObjectV4/V5` | поток `FileData`, см. ниже |
| `FirmwareUpdaterData` | только через TSS Apple (SE, Savage, Rose…). Офлайн неосуществимо; у эмулятора этих сопроцессоров нет, и запроса быть не должно |

Общее правило имени ключа: `«<имя компонента>File»`. Персонализация компонента
= `IMG4.make(IM4P из IPSW, наш тикет)`.

**`NORData`** — один словарь:
- `LlbImageData` — персонализованный `LLB`;
- `NorImageData` — **массив** персонализованных прошивок, **`iBoot` первым**
  (`plist_array_insert_item(…, 0)`); если в `Arguments` есть `FlashVersion1`, то
  вместо массива словарь «компонент → данные»;
- `RestoreSEPImageData`, `SEPImageData`, `SEPPatchImageData` — из компонентов
  `RestoreSEP`, `SEP`, `SepStage1`, если они есть в манифесте.

Список прошивок берётся из файла `<каталог LLB>/manifest` в IPSW, а если его нет
— из манифеста сборки: все записи, у которых `Info/IsFirmwarePayload`, либо
`IsSecondaryFirmwarePayload && IsLoadedByiBoot`. `LLB` и `RestoreSEP` из массива
**исключаются**: они уже уехали своими ключами.

**Поток `FileData`.** Крупные объекты (`PersonalizedBootObjectV3`,
`SourceBootObjectV4`) шлются кусками **по 8192 байта**: `{FileData: <кусок>}`,
и в конце `{FileDataDone: true}`. Имя компонента — в `Arguments/ImageName`;
особые имена `__GlobalManifest__` и `__RestoreVersion__` берутся не из манифеста.

### ASR (порт 12345 или `DataPort` из запроса `SystemImageData`)

Отдельное соединение, **плисты без длины впереди** — пишутся и читаются как
есть, XML. Порядок:

1. Гость шлёт `{Command: "Initiate", …}`; из него запоминается
   `Checksum Chunks` (bool).
2. Хост отвечает «packet info»: `Payload = {Port: 1, Size: <размер образа>}`,
   `FEC Slice Stride = 40`, `Packet Payload Size = 1450`, `Packets Per FEC = 25`,
   `Stream ID = 1`, `Version = 1`, и `Checksum Chunk Size = 131072` — **только**
   если `Checksum Chunks` включён.
3. Дальше цикл по `Command`: `Initiate` — перечитать флаг и **отправить packet
   info заново**; `OOBData` — прочитать из образа `OOB Length` байт с `OOB
   Offset` и отдать **сырыми**; `Payload` — выйти из цикла.
4. Образ идёт кусками **по 131072 байта**; если включён `Checksum Chunks`, за
   каждым куском следуют **20 байт SHA-1** от него.

Размер и чтение — по `IPSW.rangeOfStored`: образ лежит в архиве без сжатия, и
ASR читает из него по произвольным смещениям, ничего не распаковывая.

## Рестор iOS 14 прошёл целиком (15 сентября 2026)

Стенд: `<scratch>/restoretest` — `GuestUSB.swift` + `RestoreClient.swift` +
`IPSW.swift` + `IMG4.swift` с заглушками `L()`, `VMConfig`, `LogCapture`;
эмулятор — `DATA=<набор 14> ACCEL=hvf netlab/lab16.sh restore`. Архив —
`iPhone11,8,iPhone12,1_14.0_18A5351d_Restore.ipsw`, набор — копия
`~/inferno-ios/ios14ab` с обнулённым `root`.

Весь рестор — **11 минут 42 секунды**, от `StartRestore` до «гость доложил, что
закончил». Порядок запросов, как их видел гость:

```
RootTicket → NORData → FDRTrustData → SystemImageData (ASR, 4916 МБ, 9 мин)
→ PersonalizedData → IsFUDFirmware (13 штук) → KernelCache → DeviceTree
→ NORData → StatusMsg 0
```

Диск вырос до 7,8 ГБ. Затем `netlab/lab16.sh boot` на этом же диске: ядро,
APFS (`disk0s1`, транзакции идут), launchd и userspace живы, паники нет.
**Восстановленная система грузится.**

Чего в клиенте не было и что дописано по ходу: `PersonalizedData`, `FUDData`,
`EANData` (все три — один обработчик `imageData`, как `restore_send_image_data`
в эталоне) и `FirmwareUpdaterPreflight` (пустой словарь). Без них рестор падал
на `update_iBoot`.

## Скорость передачи: 10 МБ/с, и почему NVMe больше не нужен

Померено на живом ресторе iOS 14 (18A5351d), не прикидкой:

| | было | стало |
|---|---|---|
| Скорость образа | 518 КБ/с | **10 294 КБ/с** |
| Время в отправке | 2 % | 31 % |
| Ожидание окна | 96 % | 54 % |

**Виновником был не USB и не гость, а собственное ожидание.** Окно устройства —
128 КБ; отдав его, хост ждёт подтверждения. Ждал он в `serviceMux(timeout:)`,
который **досиживал все 200 мс**, даже разобрав подтверждение на первой
миллисекунде. Выходил пинг-понг «16 КБ и двести миллисекунд тишины». Теперь
`serviceMux` возвращается, разобрав пакет, а отправитель сразу смотрит на окно.
Образ 5,15 ГБ уезжает за **9 минут** вместо 2,7 часа.

**Пакет больше 16 КБ гость не берёт.** Проверено: с 48 КБ (как шлёт `muxd.py`)
устройство перестаёт принимать вовсе и рестор умирает на `NORData`. Приёмный
буфер mux-драйвера — 16 КБ, это `USB_MRU` из usbmuxd. В `muxd.py` 48 КБ сходят
с рук только потому, что через него никогда не гнали больше пары мегабайт.

**NVMe отпал.** Лишний namespace давал 7,8 МБ/с — меньше, чем USB сейчас. Затея
с подменой приёмника в RAM-диске дала бы замедление; ниже — почему она вообще
рассматривалась.

## Почему образ идёт через USB, а не через NVMe

Спрашивается само собой: перенос файлов в гостя быстрее всего идёт лишним
namespace NVMe (7,8 МБ/с против ~500 КБ/с у USB-сети). В ресторе так нельзя, и
вот почему.

- **Принимающая сторона — не наш код.** Это `asr` из RAM-диска Apple; он читает
  ровно то соединение, которое назвал ему `restored` (`DataPort`, иначе 12345).
  Сказать ему «возьми с блочного устройства» в протоколе нечем, а шелла, которым
  можно было бы прочитать namespace самим, в RAM-диске нет.
- **Мимо гостя тоже не записать.** В архиве лежит не готовая APFS, а сырой поток
  lzfse: `096-56967-082.dmg`, 4 922 702 471 байт, в zip **без сжатия**, первые
  байты `bvxn`. Разворачивает его и раскладывает по разделам сам ASR, а дальше
  рестор делает разметку, sealed system volume с root hash, NOR, SEP,
  effaceable. Повторить это на хосте — значит написать свой ASR и свою APFS.
- **Цифра 500 КБ/с — не про этот путь.** Она про CDC-NCM: гостевой TCP-стек и
  агент в userspace. usbmux идёт иначе и **не мерен**; мерить до выводов.

Если скорости всё же не хватит, рычаги в порядке дешевизны:

1. **MTU мукса.** `muxd.py` гоняет 48 КБ за пакет (`USB_MTU = 3 * 16384`), а
   `GuestUSB` — 16 КБ и туда, и обратно: три пакета на ту же работу.
2. **Подменить приёмник.** RAM-диск мы подписываем сами, тикеты уже форжатся —
   значит, в нём можно заменить `asr` своим приёмником, который читает образ из
   второго namespace NVMe, а через usbmux гонять только команды. Прав в режиме
   рестора хватает: там всё и так root. Это отдельная работа заметного размера.


## Рестор на телефоне: стена на 24 % (15 сентября 2026, вечер)

**Что работает на телефоне.** iPhone15,4, iOS 27.0, 5,6 ГБ памяти; гостю 2 ГБ,
`tb-size=384`, TCG. Подготовка набора из `.ipsw` — **целиком и за 12 секунд**
(девять дисков, 116 файлов, тикет AP 8931 Б, прошивка SEP 7 791 374 Б). Рестор
доходит до передачи образа:

```
RootTicket → NORData → FDRTrustData → SystemImageData
→ ASR на 12345 (со второй попытки) → образ провалидирован → передача
```

**Стена.** Три прогона подряд обрываются на `ASR RESTORE PROGRESS: 24%`
(≈1,24 ГБ отданного из 5 155 389 281). Гость **жив и цел**: в его консоли ни
паники, ни ошибки ввода-вывода — он просто ждёт данных, которые перестали
приходить. Журнал приложения обрывается на очередной периодической строке, то
есть **умирает приложение**, а не машина.

### Что уже исключено

- **Место на диске.** 45,9 ГБ свободно, пишется в журнал с самого начала.
- **Расширения песочницы.** В первом прогоне журнал был залит
  `sandbox_extension_consume failed: 12 (Cannot allocate memory)` — это
  разрешение закладки на `.ipsw` на каждой перерисовке (ход публиковался на
  каждый кусок образа, ~80 раз в секунду). Починено: закладка резолвится один
  раз, ход публикуется не чаще 4 раз в секунду, `BuildManifest.plist`
  разбирается один раз. **Ошибка из журнала исчезла, стена осталась.**
- **Урезание памяти гостя.** Проверено на стенде: с `MEM=1G` гость паникует по
  сторожевому таймеру (`wdog panic`) ещё до старта ASR. 2 ГБ — около минимума,
  этот рычаг закрыт.
- **`cache=none` на диске устройства.** Идея была верная (грязные страницы от
  записи образа считаются приложению), но **приложение умирает мгновенно при
  пуске**: QEMU на плохой параметр диска вызывает `exit()` прямо в нашем
  процессе. Откачено. Если возвращать — проверять на стенде и ловить ошибку
  до запуска.

### Что сейчас в сборке для следующего прогона

Замер в журнал **каждые 15 секунд во время передачи**:

```
Рестор: Образ системы 12.4 %, память 2840 МБ, свободно 45.8 ГБ
```

До этого цифра была одна и до передачи: **1645 МБ**. Права на увеличенный лимит
памяти (`com.apple.developer.kernel.increased-memory-limit`,
`extended-virtual-addressing`) в `app/Resources/entitlements.plist` **уже есть**.

### Стена объяснена (17 сентября 2026): jetsam, лимит ровно 3 ГБ

**Доказано отчётами iOS**, не догадкой (Настройки → Конфиденциальность и
безопасность → Аналитика и улучшения → Данные аналитики):

- `JetsamEvent-2026-09-15-211306.ips`: процесс `Inferno` дважды подряд (два
  разных PID — два перезапуска рестора) убит с `"reason": "per-process-limit"`,
  `rpages: 196608`. При `pageSize: 16384` это `196608 × 16384 = 3 221 225 472`
  байт = **3072 МБ ровно** — совпало на обоих PID, значит это не текущий
  footprint в момент снимка, а сам **жёсткий потолок** для этого процесса.
  `increased-memory-limit` на iPhone15,4 (5,55 ГБ ОЗУ) даёт не «где-то
  4–4,5 ГБ», как предполагалось раньше, а ровно **3 ГБ**.
- `Inferno.diskwrites_resource-2026-09-15-210300.ips` (не убийство,
  `"Action taken": "none"`, но объясняет механизм): за время рестора
  приложение «испачкало» **1074,57 МБ file-backed памяти** — запись образа в
  `root`/`root.qcow2` идёт обычным `write()` через page cache, и каждый
  записанный мегабайт оседает dirty-страницей, засчитываемой в footprint
  приложения, пока система не сбросит её на диск.

**Арифметика стены:** 2 ГБ гостя + 384 МБ буфера трансляции + ~200 МБ самого
приложения ≈ 2,6 ГБ база — на грязные страницы записи образа остаётся
~400 МБ, что и совпадает с обрывом на ~24 % (1,2 ГБ из 5,15 ГБ).

Не «Game Mode» — твит без технического подтверждения: официально Game Mode
это только приоритет CPU/GPU и удвоенный опрос Bluetooth, к памяти отношения
не имеет.

### `cache=none` на `root` попробован (17 сентября 2026) — не помог, стало хуже

Идея была в диске: писать образ восстановления в обход page cache, раз
диагностика показала file-backed dirty-память. Патч — `cache=none` на диске
`root`, только во время рестора (обычная загрузка не тронута, отдельно
проверена — грузится).

**Результат — два чистых прогона подряд, оба хуже старого:**

| | до передачи | % | память | МБ на 1 % |
|---|---|---|---|---|
| без правки (15.09) | 1645 МБ | 12,4 % | 2840 МБ | **96** |
| с `cache=none`, прогон 1 | 1658 МБ | 10,5 % | 2848 МБ | **113** |
| с `cache=none`, прогон 2 | 1667 МБ | 10,6 % | 2859 МБ | **113** |

Рост на процент передачи не упал, а вырос — два прогона с `cache=none` совпали
между собой почти до МБ, так что это не шум. Стена сдвинулась с 24 % на
**12–13 %** — хуже, не лучше. Оба раза гость был жив (ASR у себя в логе шёл
дальше, до 16 %), умирал именно хост-процесс, без единого `JetsamEvent`/
краш-репорта в системе (то есть память гуляла, но не жетсам-килл — либо это
он, просто отчёт не успел дойти до Data аналитики; см. ниже).

**Правка откачена** (`VMConfig.swift`, `root`-диск обратно без `cache=none`).

**Вывод: дело, скорее всего, не в page cache записи, а в памяти гостя.**
`cache=none` заставляет диск гонять bounce-buffer под выравнивание O_DIRECT —
это anonymous-память, которую jetsam считает тяжелее, чем чистые вытесняемые
file-backed страницы page cache. Убрав page cache, мы не сняли вес с
footprint, а переложили его в более дорогую для jetsam категорию — отсюда и
рост на процент. Более вероятный настоящий виновник — 2 ГБ гостя, которые сам
гость трогает по ходу работы ASR внутри себя (это тоже anonymous-память со
стороны хоста, растёт независимо от режима кеша диска). Это уже не рычаг,
доступный со стороны диска.

**Не проверено и стоит сделать в следующий заход:** поймать `JetsamEvent`
именно с точным временем следующего обрыва (в этот раз не нашли — ни у 13 %,
ни у 16 % прогонов отчёта не оказалось в Данных аналитики) и посмотреть разбивку
`memoryPages` (`anonymous` против `fileBacked`) в момент убийства — это
подтвердит или опровергнет гипотезу про гостевую память однозначно, вместо
рассуждений по счётчику footprint.

### Живой рестор 16.3.1 на маке (15 сентября 2026, ночь): дошли до запечатывания

**Путь выбран: `idevicerestore` + `muxd.py` + `tssd.py` на маке** (не swift-клиент).
Комплект `~/inferno-ios/ios1631` (диски, тикеты, SEP, ключи 20D67, шаблон Cryptex1,
сам IPSW 6,16 ГБ, `runs/` с логами). 16.3.1 под HVF **паникует так же, как 16.6.1**
(`instr=201420`, GENTER), поэтому рестор идёт под **MTTCG** (`ACCEL=tcg TB=256`,
гостю 4 ГБ). Окно — `GUI='sdl,show-cursor=on'` (cocoa в `build-macos` отключён).

Пройдены **четыре** барьера подряд, каждый — реальный баг, все починены:

1. **`Unable to discover device type`.** Гость представляется `n104dev`
   (dev-fused). Пропатчен `idevicerestore` (`restore.c`, `restore_get_irecv_device`):
   суффикс `dev`→`ap` перед `irecv_devices_get_device_by_hardware_model`. Пересобран
   (`make` в `tools/idevicerestore/src`).
2. **Рестор падал на `NORData`.** `muxd.py` слал mux-пакеты по 48 КБ, а приёмный
   буфер гостя 16 КБ. `USB_MTU = 16384`. (То же, что в `GuestUSB.swift`.)
3. **Образ рвался на ~96 % (1100, «failed to restore an APFS image»).** ASR-сокет
   (порт 12345) закрывался до того, как гость дочитывал хвост: `idevicerestore`
   закончил слать и закрыл, а `muxd` не дренировал очередь. `ASR: Socket
   unexpectedly closed ... backing store read ... error 9`. Починка в `muxd.py`:
   по закрытию клиента не слать RST сразу (`_drop`), а пометить `closing`,
   дослать `outgoing`, дождаться `tx_seq == tx_acked`, послать **FIN**, потом
   закрыть. После этого весь образ (4,9 ГБ) и **оба криптекса** (SystemOS ~2,9 ГБ,
   AppOS) уходят полностью.
4. **Тикет Cryptex1 (#305).** `tssd.py` подписал его на лету — **это работает**:
   `idevicerestore` принял тикет и залил криптексы через второй проход ASR.

**Где встали — `seal_system_volume` (последний шаг, прогресс 97 %).**
Гость запечатывает системный том и аутентифицирует компонент **`msys`**
(`Ap,SystemVolumeCanonicalMetadata`, mtree) через **`img4_firmware_execute`**:

```
authenticating firmware on chip: 4cc = msys
Img4DecodePerformTrustEvaluationWithCallbacks: 4cc = msys, dr = [-1 unknown]
trust evaluation failed: dr = -1, ct = 0xaaaaaaaa
calling out to execution context: 80
img4_firmware_execute failed: 80
→ CHECKPOINT FAILURE:(FAILURE:6) seal_system_volume (failed to seal system volume)
```

Проверена и **отвергнута** гипотеза «неверный дайджест `msys`»: в нашем AP-тикете
`msys` действительно был чужим (`create_apticket.py` мапил на
`SystemVolumeCanonicalMetadata`, а в манифесте 16 ключ `Ap,SystemVolumeCanonicalMetadata`).
Починено (в `create_apticket.py` добавлен fallback на префикс `Ap,`; `isys`/`rosi`
и так совпадали). **После починки ошибка бит в бит та же** (`dr=-1, ct=0xaaaaaaaa`)
— значит дело не в дайджесте, а в подписи.

**ГЛАВНОЕ (уточнено 16 сентября): проверка запечатывания идёт в USERSPACE, а не
в ядре.** `restored_external` в RAM-диске зовёт `img4_firmware_execute` из
**`usr/lib/libimg4.dylib` самого RAM-диска** — там же строки «trust evaluation
failed», «calling out to execution context» и `Img4DecodePerformTrustEvaluation…`.
Патчи ядра эмулятора (в т.ч. `allow unsigned firmware in img4_firmware_evaluate`)
на seal **не влияют вовсе**. Доказано: пробовал в ядре и снять `…Internal`, и
форсить dr-load (`ldr w20,[x23,#0x170]→mov w20,#0`) — ошибка **бит в бит та же**.
Обе ядерные правки **откачены, форк чист** (`git diff hw/arm/kernel_patches.c` пуст).

`isys`/`rosi` (образ, ядро) проходят с тем же тикетом, потому что их путь —
`img4_firmware_evaluate`; `msys` (метаданные тома) при запечатывании идёт через
`img4_firmware_execute`, которому вердикт evaluate возвращается ненулевым.

**Что в libimg4 (символы есть, `nm -n libimg4.dylib`):**
- `_img4_firmware_execute` @ `0xa2f4`: на `0xa338` зовёт `_img4_firmware_evaluate`
  (`0xa4fc`), на **`0xa33c cbz w0,#0xa348`** уходит в ошибку при ненулевом вердикте.
- внутренний evaluator — `…Internal` @ `0x1dea4` (тот же паттерн `orr x1,x9,#0xe00`
  на `0x1e048`, что и в ядре). Локальная ячейка вердикта в evaluate — `[sp,#0x1b8]`,
  инициализируется в **−1** на `0xa5d8 mov w8,#-1; 0xa5dc str w8,[sp,#0x1b8]`.
- функция-логгер «trust evaluation failed» (читатель dr) пока не локализована:
  строка `0x2c811` адресуется через пул/таблицу, ADR/ADRP+ADD её не ловит.

**Проба патча RAM-диска (16.09):**
- Эмулятор грузит **raw** RAM-диск через `-initrd` без проверки хэша; в `lab16.sh`
  добавлен override `INITRD_FILE`. RAM-диск распаковывается `img4 -i <dmg> -o
  ramdisk.raw`, монтируется RW (`hdiutil attach -imagekey
  diskimage-class=CRawDiskImage`), правится по файловому смещению, синкается.
- **Широкий патч** (`0xa33c cbz→b`, execute игнорирует вердикт) — RAM-диск грузится,
  но рестор рвётся **раньше seal**, на `-256 (Could not read data)` сразу после
  образа+`BuildIdentityDict`; гость уходит в бут-цикл. **Изоляция (raw + БЕЗ
  патча) — `-256` НЕ воспроизводится**, рестор идёт как с `.dmg` (образ →
  криптексы → seal). Значит `-256` давал именно широкий патч: `img4_firmware_execute`
  зовётся и до запечатывания, и пропуск его ветки роняет `restored`. **raw-формат
  ни при чём.**

**Глобальный обход img4 в libimg4 — тупик (16 сентября, две пробы, обе откачены):**
- широкий `0xa33c cbz→b` (execute игнорирует вердикт) — рестор рвётся **раньше
  seal** на `-256`, гость в бут-цикл;
- точечный `0xabd4 mov x0,x21→mov x0,#0` (`img4_firmware_evaluate` всегда
  возвращает 0; единственный `retab`@0xabf4, `x21` — код возврата) — тоже раньше
  seal: restored **сам вызвал `/sbin/reboot`** после «Captured preboot partition»
  (чистая перезагрузка, не паника), затем `-256`.

Изоляцией доказано: **raw-формат RAM-диска ни при чём** (raw без патча доходит до
seal, как `.dmg`). Причина обоих провалов: `img4_firmware_evaluate`/`execute`
зовутся и **до** запечатывания (BuildIdentityDict, preboot, boot-objects — без
verbose-лога), и глобальный форс вердикта уводит restored с правильного пути.

**Верный путь — чинить вход `msys`, а не обходить проверку.** Доказательства:
- За весь рестор `msys` — **единственная** полная trust-eval
  (`grep 'authenticating firmware on chip'` в госте даёт только её; `isys`/`rosi`
  через этот путь вообще не идут). Значит подпись нашего тикета до seal никто не
  проверяет — и глобальный обход не нужен и вреден.
- `dr = -1, ct = 0xaaaaaaaa` (неинициализированный ct) — это **ранний обрыв
  оценки**, а не вердикт «не доверяю». В логе рядом: `ramrod_get_trusted_img4_payload:
  im4m is NULL. Assuming payload with attached manifest`. На seal restored генерит
  mtree тома (`/mnt5/mtree_remap.xml`) и строит/читает img4 для `msys`; im4m не
  находит, предполагает вложенный — и оценка рвётся рано.

**Разбор оценки (16.09):** `…Internal`@0x1dea4 в libimg4 возвращает коды 6/7 или
ошибку под-вызова (не −1); `dr=-1` («unknown») ставит вызывающий, когда решения
нет. То есть один из img4-колбэков окружения на `msys` вернул ненулевое → ранний
выход. Какой — без исходников `restored` и live-отладки в госте не видно. Ошибка
**не зависит** от дайджеста msys (правка ничего не изменила).

**LocalPolicy проверена и отпала (16.09):** в логе гостя нет ни одной ссылки на
LocalPolicy/lpol; seal пишет devicetree/iBoot/root_hash в preboot как обычную SSV,
без policy-файла для `msys`. Так что seal msys — это чистая img4-оценка, а не
политика.

**Реалистичные пути (это фронтир — ChefKiss публично рестор 16 не сделали, #305;
msys/seal решает их закрытый симулятор сервера подписи):**
1. **msys-таргетный обход libimg4** (не глобальный — тот ломает restored, т.к.
   evaluate/execute зовутся и до seal): live-отладка libimg4 в госте (какой колбэк
   окружения даёт ненулевое для 4cc=`msys`), затем обойти только этот путь. Нужен

### Тикет Cryptex1 без Apple: `netlab/tssd.py` (15 сентября 2026)

**Почему это отдельная работа.** С iOS 16 система едет в криптексах
(`Cryptex1,SystemOS`, `Cryptex1,AppOS` и их том/trustcache), и каждому нужен свой
тикет. AP-тикет мы подделываем заранее и отдаём `idevicerestore` через `-T`, а
тикет Cryptex1 устройство просит **посреди рестора**: `restored` шлёт хосту
`FirmwareUpdaterData` c `MessageArgUpdaterName = Cryptex1`, `idevicerestore`
превращает это в TSS-запрос на `gs.apple.com`, Apple неподписанную сборку не
подписывает — и рестор умирает (issue #305).

**Решение — свой сервер подписи, только для эмулятора.** `netlab/tssd.py`:
HTTP-сервер, `idevicerestore` направляется на него флагом `--server
http://127.0.0.1:8888`. На запрос Cryptex1 отвечает подделанным IM4M:

- **Дайджесты компонентов берутся прямо из `BuildManifest.plist`** — значит
  совпадают с образами криптексов, которые пишет ASR. Для эрейза iPhone это шесть
  штук: `caos casy trca csos cssy trcs` (Rosetta-компоненты у телефона в
  манифесте есть не всегда; сервер кладёт только те, что реально в манифесте).
- **MANP-идентичность** (`fchp`=Cryptex1,ChipID=0xFF10, `clas`=ProductClass=0xF2,
  `type`/`styp`, `pave`/`vnum`=Cryptex1,Version) ставится из тегов сборки.
  У криптекс-тикета **нет ECID** — он привязан к «виртуальному чипу» 0xFF10, а не
  к устройству.
- **Подпись и сертификаты** наследуются из шаблонного IM4M и невалидны — ровно
  как у нашего AP-тикета; их снимает патч ядра `allow unsigned firmware in
  img4_firmware_evaluate`.

**Шаблон** — любой Cryptex1 IM4M как донор формы; все опознавательные поля
переписываются. Свой у мака лежит в
`/System/Volumes/Preboot/<UUID>/cryptex1/current/apticket.*.im4m`; копия для
стенда — `~/inferno-ios/ios1631/cryptex_template.im4m`.

**Чем проверено (offline, без прогона рестора).**

- Форж из манифеста 16.3.1 + шаблон: IM4M на 3224 Б, шесть компонентов, **все
  дайджесты сходятся с манифестом**, MANP `fchp/clas/type/styp/pave/vnum`
  совпадают с тегами сборки.
- HTTP end-to-end: синтетический запрос как у `idevicerestore` → ответ
  `STATUS=0&MESSAGE=SUCCESS&REQUEST_STRING=<plist>` с ключом `Cryptex1,Ticket`,
  вытаскивается так же, как это делает libtatsu.
- `img4lib` принимает подделку как манифест (`-M`) и персонализует ей DeviceTree
  без ошибок — значит IM4M структурно валиден для всей цепочки img4.

**`--server` не ломает AP-путь.** При `-T` `idevicerestore` строит `client->tss`
из файла тикета и **пропускает большой TSS-запрос** (`get_tss_response`);
персонализация загрузочных объектов идёт из этого тикета, а не новым запросом. За
время эрейза на сервер приходит только Cryptex1. Любой другой `UpdaterName`
`tssd.py` отклоняет `STATUS=94`, чтобы это было видно.

**Что осталось — прогнать вживую на полном IPSW 16.3.1.** Команда напечатана
`lab16.sh restore` (запустить `muxd.py`, потом `tssd.py`, потом `idevicerestore
… --server http://127.0.0.1:8888`). Открытые риски: (1) нонс — устройство даёт
`Cryptex1,Nonce`, сейчас сервер его только логирует, в тикет не кладёт; если SEP
проверит anti-replay, добавить нонс в MANP; (2) `Cryptex1LocalPolicy` — на
эрейзе 16 может не запрашиваться, обработчик под него не написан. Оба лечатся
после первого живого запроса.

## Грабли, которые уже стоили времени

- Эмулятор набирает USB-сокет **один раз при старте** — слушать надо раньше него,
  а поднятие устройства повторять на том же соединении.
- Серийник устройства приходит с управляющими символами: plist на них падает.
- В подделке тикета переворачивается **имя-строка внутри `SEQ`** у
  `rfta/ftap/rfts/ftsp`, а не приватный тег вокруг.
- Компонент, которого нет в манифесте (в 16 это `SystemVolumeCanonicalMetadata`),
  надо **пропускать**, а не считать ошибкой.
- **Потоковая распаковка zip обрывалась молча**: цикл выходил, пока декодер ещё
  был должен отдать хвост, и RAM-диск получался на мегабайт короче без единой
  ошибки. Правильно — крутить `compression_stream_process` до `END`, держа
  входной буфер живым между вызовами (декодер хранит на него указатель).
- **`GuestUSB` не работал ни разу, и обе поломки нашлись только на живом госте.**
  (1) NAK на чтении (`readMux`) считался ошибкой и валил подъём устройства —
  в `muxd.py` это «данных пока нет», и всё. Теперь `Failure.notReady` ловится
  только там, где читали «на всякий случай». (2) Номер mux-пакета присваивался
  **вне блокировки**, а шлют два потока — тот, что передаёт, и тот, что отвечает
  устройству; номера расходились с байтами, и гость писал
  `detected duplicate packet. Expected 9 received 13`. Теперь весь исходящий
  пакет уходит под `NSRecursiveLock`; дубликатов стало ноль. В `muxd.py` этого
  нет по построению: весь USB там на одном потоке.
- **Окно устройства в mux нельзя игнорировать.** `GuestUSB` слал данные, не глядя
  ни на подтверждения, ни на окно, — на мелких плистах это сходило с рук, а
  образ системы так не отдать: retransmit нигде не написан, и всё, что ушло за
  окно, пропадает молча. Логика взята из `muxd.py` (`rx_win`, `tx_acked`,
  `in_flight`), она там была с самого начала.
- **Файла `Firmware/all_flash/manifest` в IPSW больше нет** (проверено на 16.6.1):
  список прошивок для NOR берётся только из манифеста сборки, и ветку с файлом
  повторять незачем.
- Булевы значения в `SupportedDataTypes`/`SupportedMessageTypes` **не означают
  «хост умеет»**: половина того, что приходит и обрабатывается, стоит там в
  `false`. Таблицы копируются из Apple Configurator дословно.
- ASR отвечает **плистами без длины впереди**: читать надо до `</plist>`, и в
  одном чтении может прийти больше одного сообщения.
- `pgrep -f qemu-system` в цикле ожидания находит сам цикл — ждать по pid.
- `info cpus` в QMP показывает pid процесса, а не потоки: MTTCG не проверять по нему.
- `DYLD_LIBRARY_PATH` из `~/.zshenv` роняет `actool` и ImageIO — сборочные скрипты
  теперь его снимают.
- **`img4 -v` на SEP 20D67 не печатает `none` вовсе** — только hex-дамп одной
  строкой, и `tail -n 1`, как в `prep.sh`, отдаёт его в `-V`. Выходит IM4P с
  мусорной версией, без единой ошибки; поймано только разбором готового файла.
  Для iOS 16 передавать `-V none` прямо — так и делает `SEPFirmware.swift`.

### Проба `…Internal → return 0` в libimg4 RAM-диска (16 сентября, важно)

Аналог рабочего патча ядра, но в userspace libimg4 (`0x1dea4 pacibsp;sub` →
`mov w0,#0; ret`). Результат нов и показателен:
- рестор **не рвётся раньше seal** (в отличие от широких патчей) — прошли образ,
  криптексы, дошли до `seal_system_volume`. Значит `…Internal` **не на** пути
  «нормальных ненулевых» предшествующих проверок — короткозамыкать её по стадии
  безопасно.
- на `msys` **исчезло** «img4_firmware_execute failed» — проверка больше не
  отвергает;
- НО `restored` **падает с SIGBUS** (`restore-child-failures={initial:SIGNAL(10)[REBOOT]}`,
  `restored exited 0xa due to signal 10`) сразу после «chip disallows mix-n-match»,
  не залогировав вердикт.

**Вывод:** `…Internal` обязана заполнить выходную структуру решения; мгновенный
`return 0` её не заполняет → вызывающий читает мусор → SIGBUS. Короткозамыкание не
годится. **Нужно дать функции отработать целиком и поменять только записываемое
значение вердикта (−1 → 0).**

**Хорошая новость про загрузку:** boot-time проверку root hash ядро эмулятора уже
снимает (`bypass root hash authentication`), так что поддельная печать тома на
загрузке не отвергнется — значит обойти именно restore-time проверку `msys`
достаточно для загружаемой системы.

**Следующий шаг:** найти в `…Internal` (0x1dea4) место, где по неуспеху пишется
вердикт (или где вызывается «execution context»/сток решения), и заменить
записываемое «−1/fail» на «0/trusted», не трогая заполнение остального выхода.
Ветка ошибок Internal: `0x1e124` (эпилог), `0x1e14c` (ret 6), `0x1e154` (ret 7);
паттерн окружения `orr x1,x9,#0xe00…` на `0x1e048`. Лог: attempt9-internalzero-guest.log.

### Заглушка переходов в `…Internal` (attempt 10) и окончательный вывод

Заглушил все 11 `cbnz w0,#0x1e124` + `0x1e068 cbz→b` (дать `…Internal` отработать,
игнорируя провалы) — **опять SIGBUS**, причём **раньше**, чем при `Internal→0`
(сразу после «chip disallows mix-n-match», до «wrapped Image4 payload»). Значит
**ранний** колбэк декода `msys` тоже возвращает ошибку, и без его настоящего
вывода продолжать нельзя.

**ОКОНЧАТЕЛЬНО: байт-патчами libimg4 seal `msys` не берётся.** Перепробованы пять
стратегий, все откачены:
1. `execute 0xa33c cbz→b` — ломает предшествующую фазу (`-256`, бут-цикл).
2. `evaluate 0xabd4 mov x0,x21→#0` — ломает (restored сам перезагружается рано).
3. `…Internal 0x1dea4 → mov w0,#0; ret` — SIGBUS (не заполнен выход).
4. `…Internal` все `cbnz`-переходы → NOP — SIGBUS (ранний колбэк оставляет мусор).
5. (в ядре) dr-load `mov w20,#0` — не тот бинарь, seal в userspace.

Провальный колбэк — код **`restored_external`** (окружение img4), а не libimg4;
без его настоящего вывода оценку `msys` не подделать байт-патчем библиотеки.

**Реальные пути дальше (все глубокие, отдельная работа):**
1. **Патчить `restored_external`** — найти в нём провальный img4-колбэк окружения
   для `msys` и заставить отдать «доверено» с корректным выводом. Бинарь без
   символов, но `nm`/строки помогут; RAM-диск мы правим байтами так же.
2. **Live-отладка в госте** — lldb-сервер/агент в RAM-диске, поймать, какой колбэк
   и почему даёт ненулевое на `msys`; это направит точечную правку (1).
3. **Настоящий подписанный `msys`** — ключи Apple, недоступно.

RAM-диск (`ramdisk.raw`) пересоздан из `.dmg`, libimg4 чист; форк эмулятора чист;
хост-инструменты на месте. Логи: attempt{9,10}-*-guest.log.

### Пробой seal через `img4_firmware_execute` (16 сентября, разбор бинарей)

Статический разбор `libimg4.dylib` и `restored_external` из RAM-диска
(`~/inferno-ios/ios1631/analysis/`, символы у libimg4 есть):

- Цепочка на seal: `restored_external` (`ramrod_seal_system_volume_internal`,
  0x10004e674) генерит live-mtree, оборачивает в img4 (`img4_firmware_new`,
  4cc=msys в arg2), прикладывает манифест (`img4_firmware_attach_manifest`) и
  зовёт **`img4_firmware_execute`** (единственные 2 сайта — 0x10004e994/0x10004e9e8,
  оба тут).
- `img4_firmware_execute`@0xa2f4: `bl img4_firmware_evaluate`; на **0xa33c
  `cbz w0,#0xa348`** — при успехе оценки идёт в ветку исполнения (a348),
  отдаёт настоящий payload колбэку `restored`; при провале (наш случай)
  ветвится на a3ec и зовёт колбэк с **NULL-образом и ошибкой** → печать
  «img4_firmware_execute failed: 80», seal не пломбируется.
- `evaluate`@0xa4fc возврат берёт из `__img4_firmware_evaluate_trust_object`@0x9c28
  → `Img4DecodePerformTrustEvaluationWithCallbacks` возвращает **dr=-1** (один из
  env-колбэков `restored` вернул -1 через `cbnz w0,#0x1e124` в
  `…Internal`@0x1dea4), `__img4_firmware_compute_trust_result`@0xb9d8 мапит это в 80.
- Колбэк-исполнитель в `restored` (0x10004ebe8): при не-NULL образе вынимает байты
  mtree и ставит success; при NULL — печатает ошибку. Сам APFS-seal идёт из
  `restored` уже по вынутым байтам.

**Ключевая правка премисы хендоффа:** `_img4_firmware_execute` импортирует
**только `restored_external`**, а `_img4_firmware_evaluate` — вообще никто извне
(проверено `otool -Iv` по всем бинарям RAM-диска). Значит правка
`img4_firmware_execute` в libimg4 бьёт **исключительно** по seal(msys); прежний
вывод «execute зовётся и до seal, поэтому a33c→b рвёт раньше» опирался на неверную
посылку. Объект msys: flags=5 (bit4=0, [obj+8]=0), payload в [obj+0x270] → ветка
a348→a4c4 «deliver unwrapped payload» с x21=0. Поэтому пробуем заново **глобальный
`0xa33c: cbz w0→b`** (`60 00 00 34`→`03 00 00 14`, file off = VA = 0xa33c): execute
отдаст настоящий mtree колбэку → success → реальная пломбировка; ядро на загрузке
root-hash уже не проверяет. Патч в `analysis/ramdisk.raw` (наша копия).

### Прогон с ГЛОБАЛЬНЫМ a33c→b: SIGBUS на install_splat (не на seal) — хендофф был прав

Глобальный `0xa33c cbz→b` дал **SIGBUS (signal 10) в `restored` на шаге
`install_splat` (0x06A6, прогресс 92%)**, ДО seal — ровно как предупреждал п.1
старого разбора. Причина уточнена: `img4_firmware_execute` зовётся не только из
seal, а из общего хелпера **`ramrod_get_trusted_img4_payload`** (это ЕГО строка
«im4m is NULL. Assuming payload with attached manifest», а не seal-функции), а его
зовут и `install_splat` (`_personalize_splat_ticket`), и seal. В базовом прогоне
install_splat проходил без «authenticating firmware»/execute-лога и писал
cryptex1-тикет; при форсе execute его eval-провал пошёл в плохую ветку → SIGBUS
на «prerolling splat nonce». Значит патч execute обязан быть **условным по 4cc**.

Важное различие точек провала eval: install_splat падает РАНЬШЕ раскодирования
payload (иная ветка a470 «raw payload» → мусор), а msys — ПОЗЖЕ («wrapped Image4
payload» уже залогирован, payload в [obj+0x270] есть → ветка a358→a4c4 «deliver
unwrapped»). Поэтому msys-условный форс может пройти там, где глобальный ломался.

**Применён условный патч (16.09):** code-cave в мёртвой (LocalPolicy в ресторе не
используется) `__LocalPolicyEc384Sha384_compute_digest`@0x139c:
`cbz w0,0xa348` / `ldr w9,[x19,#0x38]` / `movz w10,#0x7973;movk w10,#0x6d73,lsl16`
(=0x6d737973 'msys', подтверждено: restored материализует ровно так на 0x10004ef90)
/ `cmp w9,w10` / `b.ne 0xa340` (не-msys → оригинал) / `b 0xa348` (msys → форс).
`0xa33c` → `b 0x139c`. Только msys с провальной оценкой форсит исполнение; всё
прочее нетронуто. Прогон идёт.

### КРИТИЧНО (16.09): крэши install_splat были ПОВРЕЖДЕНИЕМ ramdisk.raw, не патчем

Три прогона подряд падали SIGBUS на `install_splat` → `_personalize_splat_ticket:
prerolling splat nonce` (внутри `img4_nonce_domain_preroll_nonce`, энтэнглинг
cryptex1-nonce с SEP UID — эмулятор «we don't know how to do that yet»). Долго
искал причину в патче. **Контроль решил вопрос:** чистый `ramdisk.raw`,

install_splat ломало **повреждение APFS в ramdisk.raw от многократных RW-монтирований**
(mount/patch/unmount 3+ раз подряд разрушает том). 

**Урок:** ramdisk.raw патчить РОВНО ОДИН раз на свежей копии из dmg; при сомнении

Вывод прошлой сессии «глобальный a33c→b ломает install_splat» — вероятно тоже
коррупция, а не форс (install_splat вообще не зовёт `img4_firmware_execute`).

### Архитектура seal (разобрано по бинарю restored_external)

- Чекпойнт seal_system_volume: `ramrod_verify_manifest_for_mountpoint_internal`
  (@~0x10004ec... , строка «Running mtree») генерит live-mtree, зовёт auth-обёртку
  **`0x10004f27c`** с 4cc=msys (0x10004ef90 `mov w2,#0x7973; movk w2,#0x6d73`),
  проверяет её результат на **0x10004efa8 `cbz w0, 0x10004f09c`** (0=провал→ошибка).
- `0x10004f27c` зовёт `ramrod_get_trusted_img4_payload` (**0x10004e674**, единств.
  вызыватель `img4_firmware_execute`), возвращает доверенный payload / статус.
- Реальную пломбировку делает ВНЕШНЯЯ утилита **`apfs_sealvolume`**
  (`ramrod_seal_system_volume_internal`@0x10004f37c: argv `-R -P /mnt5/root_hash -L
  -M -I -a -u -E -d -v`, exec на 0x10004f710, «Successfully returned after running
  apfs_sealvolume»), и она запускается ТОЛЬКО если msys-аутентификация прошла.
- Т.е. msys-auth ГЕЙТИТ apfs_sealvolume. Значит нужен либо проход auth (форс
  execute для msys — тестируется сейчас), либо правка restored, чтобы auth-провал
  не блокировал `apfs_sealvolume` (но тогда нужен реальный payload mtree, который
  извлекает именно execute — потому форс execute предпочтительнее).

### РЕШЕНО (16.09): почему mount ломал install_splat — ДЕКОМПРЕССИЯ libimg4, и фикс

Долго искал, почему любой mount+patch libimg4 роняет install_splat/preroll_nonce,
хотя чистый образ проходит. Серия изоляций дала точный ответ:
- Файлы RAM-диска лежат **decmpfs-сжатыми** (`ls -lO` → `compressed`, libimg4
  128 КБ физич. из 396 КБ; строки в raw не ищутся — прямой патч по смещению невозможен).
- **RO-mount безопасен** (версия APFS не меняется). **RW-mount на macOS 27
  бампает** том до `apfs_kext 3288.1.3` (было `1677.41.3.101.1`), НО mount-only
  (без записи, libimg4 остаётся сжатым) **проходит install_splat и доходит до seal**
  — значит бамп версии НЕ причина.
- Причина: при ЗАПИСИ в libimg4 macOS его **декомпрессирует** (снимает decmpfs).
  Разжатый libimg4 гость iOS 16 не переваривает → SIGBUS в `img4_nonce_domain_preroll_nonce`
  (0x92f0) на install_splat, ДО seal. (Не переполнение — 12 МБ свободно.
  У attempt9/10 это работало на старом macOS.)

**ФИКС: после патча вернуть decmpfs-сжатие** `ditto --hfsCompression`:
```
# на смонтированном RW томе, LIB=.../usr/lib/libimg4.dylib
python3 patch(LIB)                       # правит байты (разжимает файл)
cp "$LIB" /tmp/p; rm "$LIB"
ditto --hfsCompression /tmp/p "$LIB"     # снова compressed
chmod 0755 "$LIB"                        # ls -lO → compressed; контент = clean+патч
find "$V" -name .fseventsd -exec rm -rf {} +   # убрать мусор macOS 27
```
Проверено: `ls -lO` показывает `compressed`, дифф с чистым libimg4 = ровно 3 моих
правки. Правило: **любую правку файла в RAM-диске завершать `ditto --hfsCompression`.**

### ПРОРЫВ (16.09): блочный патч decmpfs в raw БЕЗ монтирования (обход macOS 27)

Пере-сжатие через ditto НЕ спасло — **любая запись файла кекстом macOS 27 (3288)**
пишет data-экстенты в формате, который гость iOS 16 читает неверно (SIGBUS в
preroll_nonce), сжато или нет. RO-mount безопасен (версия не меняется), RW-mount —
нет. Linux/apfs-fuse/старого macOS нет.

**Решение — патчить сжатые блоки прямо в raw-образе, не монтируя** (APFS НЕ хэширует
данные файлов, только метаданные — fletcher64; правка data-экстентов не рушит fsck
и не бампает версию). libimg4 сжат decmpfs **type 4 (zlib, 64K-чанки в ResourceFork)**.
Алгоритм (скрипт отработан, `analysis/ramdisk.raw` пропатчен, версия осталась 1677):
1. Найти блочную таблицу: искать в raw `struct.pack('<I',nb)+struct.pack('<I',4+nb*8)`
   где `nb=ceil(size/65536)` (для libimg4 nb=7 → `070000003c000000`), проверить, что
   разжатие всех блоков == чистый libimg4. Нашлась на `0x2f52104`.
   Таблица: `nb`(u32 LE), затем nb×(offset,len)(u32 LE, offset от начала таблицы),
   затем блоки (первый байт 0xFF → сырой, иначе zlib-поток).
2. Собрать пропатченный libimg4 (clean + правки a33c/cave). Изменённые байты попадают
   в блок 0 (a33c=0xa33c) и блок 2 (cave 0x21cc4).
3. Пере-сжать ТОЛЬКО эти блоки `zlib.compress(...,9)`; проверить, что новый размер
   ≤ старого (у нас 25110≤25722 и 29738≤30396 — влезает).
4. Записать новые сжатые блоки на их прежние offset в raw, обнулить хвост-зазор,
   ОБНОВИТЬ длину блока в таблице (`TAB+4+k*8+4`). Offsets блоков и суммарный размер
   не трогать. decmpfs-заголовок (magic `fpmc`, type, usize) не трогать.
5. Round-trip: пере-извлечь libimg4 из raw по таблице → должно быть ровно clean+правки.
   fsck_apfs -n → OK, «last modified by apfs_kext 1677» (без бампа).

**Правило:** правки файлов RAM-диска на macOS 27 делать ТОЛЬКО так (блочно в raw),
никогда через RW-mount. Скрипт патча — в истории сессии; можно оформить в netlab/.

### Блочный патч работает; cave в cold.1 (0x21cc4) НЕ годится — ломает install_splat

Блочный патч raw (без mount) подтверждён серией изоляций:
- `nullrc` (блоки 0/2 пере-сжаты из ЧИСТОГО libimg4, длины изменены+зазоры) →
  **проходит install_splat, доходит до seal**. Значит пере-компрессия и смена длин
  безопасны; APFS данные не хэширует, версия 1677 сохраняется.
- Полный патч (a33c + cave@0x21cc4) и `cave-only` (только cave, a33c нетронут) →
  **оба падают на install_splat/preroll_nonce**. Значит перезапись
  `_img4_firmware_evaluate.cold.1`@0x21cc4 всё-таки задевает install_splat
  (вопреки статике «cold.1 зовётся только из evaluate/seal»). Cave в cold.1 отменён.
- `_personalize_splat_ticket` НЕ зовёт execute/evaluate/get_trusted (проверено);
  почему cold.1 задевается — не до конца ясно (возможно, гостевой decmpfs-инфлейт
  чувствителен к содержимому блока 2, либо cold.1 достигается косвенно).

**Текущий подход — БЕЗ cave:** глобальный `0xa33c: cbz w0,#0xa348 → b 0xa348`
(4 байта в блоке 0, блок 2 нетронут). `img4_firmware_execute` зовётся только на
seal (msys mtree + root_hash), install_splat его не зовёт → a33c инертен до seal.
На seal форсит ветку исполнения для обоих → payload доставляется → seal идёт.
Прежний вывод «глобальный a33c→b рвёт до seal» был артефактом коррупции монтирования.

### РАЗГАДКА install_splat-крэша: проверка хэшей 16К-страниц кодовой подписи libimg4

**ЛЮБАЯ правка байтов libimg4 роняет install_splat/preroll_nonce детерминированно**
(перепроверено повторным прогоном того же образа). Механизм — code-signing проверяет
хэш каждой 16К-страницы dylib при первом исполнении кода на ней; правка «отравляет»
страницу → при доступе SIGBUS. Идеально ложится на факты (страницы 16К, iOS arm64):
- стр. `0x8000` содержит и `preroll_nonce`@0x92f0, и `a33c`(execute) → патч a33c
  отравляет страницу preroll_nonce → SIGBUS при install_splat.
- стр. `0x20000` содержит и cave `cold.1`@0x21cc4, и `__auth_stubs` (стаб
  `IOConnectCallMethod`@0x225d0, который зовёт preroll_nonce) → патч cave отравляет
  страницу стаба → SIGBUS.
- `nullrc` (пере-сжатие с ТЕМ ЖЕ содержимым) → хэши страниц не меняются → проходит.
- Прошлый вывод «attempt9/10 …Internal→0 даёт SIGBUS из-за незаполненной структуры»
  — вероятно ТА ЖЕ проверка cs: страница с 0x1dea4 впервые исполняется на seal.

Значит эмулятор ДЕЙСТВУЮЩЕ проверяет cs-хэши страниц userspace-dylib RAM-диска.
Патчить libimg4/restored НЕЛЬЗЯ без одного из: (1) правки эмулятора — отключить
cs-проверку страниц userspace; (2) пере-подписи libimg4 (codesign ad-hoc пересчитает
хэши страниц под новый контент) + добавления нового cdhash в trustcache
(`InfernoData/Restore/Firmware/098-24758-073.dmg.trustcache`, грузится как
`trustcache=` в -M). Свежий взгляд (агент) уточняет, что именно проверяет эмулятор
и какой фикс минимален.

### ФИКС (16.09): починен обход pmap_cs в эмуляторе — теперь libimg4 можно патчить

Внешний агент подтвердил и уточнил разгадку: install_splat-крэш — это PPL
code-signing (`pmap_cs`), и у самого эмулятора ЕСТЬ обход `bypass pmap_cs_enforce`,
но он **не применялся** на кернелкэше 16.3.1 (бут-лог: «did not apply in __PPLTEXT»).
Причина: паттерн ждал `bl; cbnz w0; mov x8,#-0x31d` подряд, а 16.3.1 вставляет между
ними `adrp`/`mov` (сайт `pmap_enter_options_internal`, kc.raw @0x14c610c, якорь
`88 63 80 92` = `mov x8,#-0x31d`, единственный).

**Правка `inferno-src/hw/arm/kernel_patches.c`** (ветка `ios`): `ck_kp_pmap_cs_enforce_patch`
переписан на callback — якорь на уникальном `mov x8,#-0x31d`, затем `find_prev_insn`
назад к `cbnz w0` и `bl`, `bl→mov w0,#0` + `cbnz→nop` (терпит вставки). Пересобрано
`ninja -C build-macos qemu-system-aarch64`. Бут-лог теперь: **«bypass pmap_cs_enforce
patch applied in __PPLTEXT»**. Дело было в ПАТТЕРНЕ, не в секции.

**Следствие (важно на будущее):** теперь ЛЮБОЙ байт-патч userspace-бинаря RAM-диска
(libimg4, restored_external, лог-инструкции) проходит — pmap_cs больше не убивает
процесс при первом исполнении изменённой страницы. Патч libimg4 применяю по-прежнему
блочно в raw (без RW-mount, версия APFS 1677 сохраняется). Правка эмулятора локальна
для стенда; в релиз/другие ветки — по решению (это починка собственного обхода форка).

Прогон с `/tmp/global.raw` (a33c: `cbz→b 0xa348`, форс исполнения msys/root_hash) +
починенным pmap_cs — идёт; ждём исход seal.

### ПОСТ-SEAL БАРЬЕР ПРОЙДЕН (16.09): загрузка запечатанного тома с live fs

После успешного рестора восстановленная система не грузилась: детерминированная
паника APFS `panic ... "Rooting from the live fs of a sealed volume is not allowed
on a RELEASE build" @apfs_vfsops.c:2412`. Причина: рестор запечатал том (SSV) и
создал корневой снапшот, но эмулятор грузит ядро напрямую (`-kernel`), без
iBoot-манифеста / `system-volume-auth-blob` в device tree, называющего снапшот →
`apfs_find_named_root_snapshot_xid` фейлит (81) → ядро откатывается на live fs →
RELEASE-сборка это запрещает → паника.

Разбор `kc.raw` (capstone, VA→off по сегментам; kernel slide=0, __TEXT_EXEC
vm=0xfffffff007c88000 foff=0xc84000): панику печатает `apfs_vfsop_mount`
(строка формата @0x778e026, кекст com.apple.filesystems.apfs). Единственный вход
в панику-блок @0xa08ea50 — `0xa08e6c0 tbnz w8, #5, 0xa08ea50`, где
`w8 = ldrb [x8,#0x38]` (x8 = том по [x?+0xc0]); бит 5 = «том запечатан». (Соседний
`b.ne 0xa08ea4c` — это `___stack_chk_fail`, не наша ветка; GOT-слот 0x7c69e90 =
`___stack_chk_guard`.)

**ФИКС — `hw/arm/kernel_patches.c` (ветка `ios`), в `ck_kp_apfs_patches`:** новый
`ck_patcher_find_replace` «allow rooting the live fs of a sealed volume» нопит
`tbnz w8,#5`. Паттерн: `ldrb w8,[x8,#0x38]` / `tbnz w8,#5,?` / `str xzr,[sp,#?]`
(маска гасит смещение tbnz и оффсет стора; хвостовой `str xzr,[sp]` отличает от
похожего tbnz в root-auth). Уникален во всём __TEXT_EXEC (1/37МБ). Пересобрано
`ninja -C build-macos qemu-system-aarch64`. Бут-лог: «allow rooting the live fs of
a sealed volume patch applied in __TEXT_EXEC».

**Результат:** гость впервые проходит mountroot и уходит в userspace: `launchd`,
`Early boot complete. Continuing system boot.`, `Obliterator: No obliteration
needed, continue booting`, `UMD_INIT: Regular mode Setup for user:501`, запуск
`/System/Library/CoreServices/SpringBoard.app/SpringBoard` (pid). Экран (QMP
screendump, 828x1792 = родное n104): Apple-логотип + прогресс-бар первой загрузки.
Под MTTCG медленно. Базовое состояние рестора склонировано в
`InfernoData/*.restored` (root.restored и пр., cp -c). Прогон: `DATA=~/inferno-ios/
ios1631 GUI=none ACCEL=tcg netlab/lab16.sh boot`, muxd.py должен слушать.

### SETUP ДОСТИГНУТ + разбор MTTCG-зависания и HVF-паники (16.09, поздно)

**Рестор 16.3.1 грузится до Setup Assistant («Hello»/«olá»)** после патча sealed-volume
live-fs (см. выше). Пруф — QMP screendump: статус-бар, home-индикатор, кнопка ⓘ,
курсивное приветствие. Это фронтир публичного форка ChefKiss (рестор 16 публично не
делали, #305).

**MTTCG-зависание (после появления UI).** Восстановленная 16 под MTTCG доходит до
экрана приветствий, ~минуту живёт (нормальный FPS), затем **livelock**: кадр застывает,
лог/часы стоят, 3 ядра в полке (~300% cpu) крутятся в **EL0 (userspace)** на разных PC
(не спин на локе ядра), CPU#3 запаркован на `0xffffffff0000bf24` (это НОРМА — idle-ядро,
не баг; ранний вывод про «GXF-wedge CPU#3» был ошибочным). Отвергнуто по фактам:
не порча тома DATA (виснет на чистом пристина-состоянии, storm=0), не шторм
`reset ino`, не unimplemented sysreg (в qemu-логе чисто), не WFE/event-stream
(WFE у форка — NOP, для корректности безвреден). **Диагноз: гонка конкурентности
MTTCG между ядрами.** Доказано изоляцией: `THREAD=single` (добавлен knob в lab16.sh:
`tcg,thread=${THREAD:-multi}`) с чистого пристина **проходит** мёртвую точку MTTCG
(лог +229, идёт дальше, кадр анимируется, не виснет) — там, где MTTCG железно умирает.
Первый «single тоже виснет» был испорченным тестом (грязный root → шторм → ранний
затык). Класс бага: atomics/exclusive monitor (LDXR/STXR)/барьеры/TLB-шутдаун между
ядрами — на них стоят `os_unfair_lock` userspace 16; 14 их использует иначе → под
MTTCG жива. Root-cause упирается в отсутствие символов XNU (kernelcache несёт только
kext-символы; nm по kc.raw ядро XNU не символизирует) — точку спина по PC не назвать
без источника символов ядра (KDK/симболикация) — это ключевая следующая задача.

**HVF — НЕ стена, чинибельно. Корень локализован до одного регистра.** Ключ: iOS 14
на A13 (тоже PPL/GXF, тот же `GENTER`) идёт под HVF на скорости живого iPhone 11 →
**GXF под HVF работает в принципе**. Значит прежний вывод «HVF невозможен by design» —
НЕВЕРЕН. 16 под HVF падает рано: `panic Undefined kernel instruction pc=0xfffffff007d4bcb0
instr=201420(GENTER) @sleh.c:1169`, guest line 27; в qemu-логе НЕТ `unhandled exception
ec=` → `GENTER` в EL2 не трапится, это чистый guest-side UNDEF (GXF на vCPU не включён).

Диагностика (временный `warn_report` префикс `HVFDIAG` в `target/arm/hvf/hvf.c` —
в `hvf_sysreg_write` при входе и в обоих UNHANDLED-путях; **УБРАТЬ перед коммитом**):
под HVF гость пишет Apple GXF/SPRR регистры `s3_6_c15_*`, все они **трапятся в EL2 и
проглатываются** fallback'ом `hvf_sysreg_write_cp` в `env->gxf/sprr` (software-only,
под HVF инертно — на железо не идёт; `hvf_arch_init_vcpu` GXF вообще не трогает).
Differential 14 vs 16 (оба под HVF, тот же diag-билд):
- обе пишут одинаково по составу: `c1_0/_1/_2` (SPRR/GXF config+enable), `c1_5/6/7`,
  `c3_0` (SPRR/MPRR-таблицы прав), `c8_1/_2` (guarded-векторы входа GXF, адреса ядра);
- **16 дополнительно пишет `s3_6_c15_c3_3 = 0x40000`; 14 этот регистр НЕ трогает вовсе.**
14 при том же проглатывании грузится (46942 diag-записей, alive, GENTER-паники нет),
16 — падает. Т.е. дело не в самом проглатывании (14 его терпит), а в **`c3_3`**: это
новый (пост-14) Apple GXF/SPRR-регистр (по структуре форка — область MPRR/расширенных
SPRR-прав guarded-режима), включающий расширенный режим, эффект которого под HVF до
реального ядра не доходит → железный GXF не в ожидаемом 16-м состоянии → `GENTER` undef.

**Путь к HVF-фиксу (с остатком неизвестности):**
1. Семантика `s3_6_c15_c3_3`/бита `0x40000` и чем 16 гейтит его использование (какой
   ID/feature-регистр читает — возможно, вернуть его как «фича отсутствует», чтобы 16
   шла по 14-пути без c3_3).
2. Почему GXF-регистры вообще трапятся под HVF (HACR_EL2/конфиг HV) — если не трапить
   (дать исполняться нативно), железо само включит GXF и, вероятно, 16 заработает
   (14 уже жива). Это наиболее вероятный настоящий фикс.
3. Иначе — проводить c3_3 (и весь GXF-набор) на железо через HVF-API, если тот примет
   Apple-IMPDEF кодировку.

(cp -c, откатывать всё вместе). Прогон: `DATA=~/inferno-ios/ios1631 GUI=sdl|none
ACCEL=hvf|tcg THREAD=single|multi netlab/lab16.sh boot`, muxd.py слушать. iOS 14 для

- `s3_6_c15_c3_3` в публичных картах Apple-регистров (Asahi/m1n1/Sven Peter) НЕ описан
  (подтверждает: новый пост-14 регистр SPRR/GXF-семейства). Разрешить семантику —
  дампом m1n1 (`mrs`-перебор с recovery) или чтением usage в ядре 16 (нужны символы).
- Перехват Apple GXF-регистров под HVF — **дефолт Hypervisor.framework**, не настройка
  форка: `hvf_arch_set_traps` ставит только debug-трапы, IMPDEF-трапы HV решает сам.
  Значит «не трапить GXF» нельзя; путь фикса — корректно ОБРАБОТАТЬ трапнутый `c3_3`
  (сейчас проглатывается в `env` fallback'ом `hvf_sysreg_write_cp` и на железо не идёт).
  Загадка: 14 с тем же проглатыванием всех GXF-регистров работает — значит либо GXF на
  vCPU включён по умолчанию (и c3_3 меняет режим, который HW под HVF не подхватывает),
  либо c3_3 обрабатывается иначе прочих. Не разрешено; нужен либо дамп семантики c3_3,
  либо эксперимент (пробросить c3_3 на HW / вернуть feature-ID как «нет фичи», чтобы 16
  шла 14-путём). Это уже правка+пересборка+прогон — на решение пользователя.

### ПРОРЫВ В ДИАГНОСТИКЕ MTTCG-зависания (17.09): потерянное пробуждение из WFI

Цель — **iPhone** (не Pixel 7): эмулятор в софте (TCG/MTTCG), HVF на iPhone невозможен
(виртуализации нет), так что HVF/c3_3 к цели не относятся — та ветка закрыта.
Важно: theGlym на форке-от-нашего-форка гоняет iOS 26.5 под MTTCG на iPhone Air —
значит MTTCG в принципе тянет новую iOS, и нужный фикс существует на уровне форк-кода.

**Поймал зависание с конкретной точкой (в отличие от прошлых догадок).** Прогон
16.3.1 под MTTCG встал РАНО, на boot-task `mount-phase-2` (guest line 636), cpu ~7%
(не спин — простой). Снял состояние ядер (QMP `info registers -a`):
- CPU#0/#1/#2 — все на **`PC=0xfffffff007d517f0`**, EL1; дизасм (kc.raw):
  `…7ec: wfi` / `…7f0: cbz x30,…7f8` / `…7f4: ret` / `…7f8: mov x0,#1; bl; b .` —
  это **цикл парковки ядра в WFI** (спит, ждёт прерывание/IPI, чтобы взять работу).
- CPU#3 — `0xffffffff0000bf24` (тоже запаркованное idle-ядро).
Итог: **ВСЕ 4 ядра спят в WFI, разбудить некому** → система стоит. Это классическое
**потерянное пробуждение (lost wakeup): прерывание/таймер не доставлен спящему ядру
под MTTCG.** Инструменты: `inject-nmi` на t8030 НЕ поддерживается («machine does not
provide NMIs») — форс-стек-шот так не снять; `x-query-interrupt-controllers` пуст.

**Вероятно единая причина обоих режимов:** потерянное событие; при куче готовых
потоков (после Setup) кто-то busy-спинит на локе застрявшего потока (3 ядра EL0 300%),
при малом числе (ранний boot) все уходят в WFI (idle 7%). Отсюда и недетерминизм точки
зависания. single-thread этого не ловит (проходит дальше) — подтверждает MTTCG-гонку.

**Область фикса — `hw/intc/apple_aic.c`.** Пробуждение ядер: `qemu_irq_raise(cpus[i].irq)`
из таймеров `QEMU_CLOCK_VIRTUAL` — `apple_aic_tmr_tick` (per-CPU `cpu->tmr`),
`apple_aic_tick` (глобальный `s->timer`), время — `apple_aic_emulate_timer()` от
`qemu_clock_get_ns(QEMU_CLOCK_VIRTUAL)`. Подозрительное: `apple_aic_tmr_rearm` при
`tmr_isr & AIC_TMRISR_PCT` делает `timer_del(o->tmr)` и выходит без raise; плюс возможна
MTTCG-гонка между `qemu_irq_raise` из таймер-колбэка и входом vCPU в WFI (kick теряется).
Следующий шаг (с пользователем, не вслепую): инструментировать AIC — логировать
arm/fire/rearm таймера и вход/выход WFI, воспроизвести, увидеть, какое пробуждение
теряется. Либо сравнить apple_aic.c с фиксом theGlym, если доступен.

## Рестор на телефоне: возвращаемся (17 сентября 2026, вечер)

Тема ожила заново — решение от 15.09 «отложено» больше не в силе, копаем дальше.
Порядок ниже — по факту того, что перепробовано за вечер, включая тупики.

### Тупик: `cache=none` на диске `root` — не помог, отменён

Гипотеза была верной по механизму (диагностика `.diskwrites_resource` реально
показывала гигабайты грязных file-backed страниц), но лечение оказалось не тем:
`cache=none` заставляет QEMU гонять bounce-buffer под выравнивание O_DIRECT —
это тоже anonymous-память, и jetsam считает её даже тяжелее, чем грязные
file-backed страницы. Два чистых прогона подряд дали **113 МБ/%** вместо
прежних **96 МБ/%** — хуже, не лучше. Откачено.

### Тупик: возврат `mtxspin=-1` для рестор-загрузки — тоже не помог

Гипотеза: `bootArguments` (уже в дереве до этой сессии) убрал `mtxspin=-1`
глобально ради MTTCG-фикса после Setup, но действует и на рестор-загрузку
RAM-диска, где не проверялся. Вернул `mtxspin=-1` только когда
`restoreRamdiskPath != nil`. Тот же прогон, то же место обрыва (~13% гостевого
счётчика). Откачено — эффекта нет, а лишний код держать незачем.

### Настоящая причина стены на 24% → 13-16%: не в диске и не в памяти гостя

Три прогона той же ночи (13.09→17.09) с одним и тем же кодом дали **другую**
точку обрыва (24% раньше, 13-16% сейчас) при идентичном росте памяти —
подозрение упало на day-to-day разницу в свободной памяти телефона, а не на
код. **Не доказано окончательно**, тема не закрыта, но обе правки диска/spin
выше — точно мимо.

### Найдено и почти наверняка объясняет все «мгновенные вылеты без единого отчёта»

Ни один «вылет» этой ночи не оставил ни `JetsamEvent`, ни `Inferno-*.ips` —
кроме одного настоящего краша (JIT/`tcg_region_init`, разовая заминка,
см. ниже). Причина: **это не краш вообще**. `ContentView.body` в
`InfernoApp.swift` показывал `SetupView` по условию
`if !model.missing.isEmpty` — а `model.missing` пересчитывается через
`model.refreshFiles()`, который `RestoreKitSetup`/`RestoreSettings` дёргают
как `onReady()` сразу по завершении «Подготовить набор». Как только
подготовка дописывает последний нужный файл (в т.ч. `sep_ssc`, который в
`requiredFiles`), `missing` пустеет — и SwiftUI **мгновенно убирает
`SetupView`** из дерева, открывая главный экран позади. Ни краша, ни kill —
просто штатная логика показа экрана сработала посреди того, как человек на
неё смотрел. Воспроизведено вживую на маке и понято по свежим логам
(процесс жив, PID тот же, самый новый краш-репорт — многочасовой давности).

**Первая правка была слишком широкой и откачена.** Расширение условия на
`|| model.needsRestore` держало `SetupView` на главном экране **весь рестор**,
а не только до первого набора — и тут же вскрылась вторая проблема:
`RestoreKitSetup` встроен в `SetupView` (главный экран) и отдельно в
`RestoreSettings` (Настройки → Восстановление) как **два независимых
экземпляра**, каждый со своим `@State` (тикет, ROM). Человек выбирал файлы в
одном месте, а с `needsRestore`-правкой на главном экране вдруг снова
показывался ДРУГОЙ, пустой экземпляр того же экрана — выглядело как «всё
слетело», хотя процесс был жив (проверено: тот же PID). Дальше это было
принято за куда более драматичную теорию (iOS убивает процесс в фоне) —
тоже мимо: объяснение оказалось проще, и это была правка этой же ночи.

**Правка (исправленная версия):** условие показа `SetupView` вернули как было
(`if !model.missing.isEmpty`). Сама причина мгновенного исчезновения на слове
«Готово» устранена по-другому — `onReady` в `RestoreKitSetup` внутри
`SetupView` теперь дёргает `model.refreshFiles()` не сразу, а через 2 секунды
(`DispatchQueue.main.asyncAfter`), так что человек успевает прочитать
последнюю строку до того, как экран уйдёт.

**Не объяснено ни одной из версий этой правки**: вылеты **во время самой
передачи образа** (13%, 16%, 56% на телефоне) шли с экрана Настройки →
Восстановление (`.sheet`), а не с `SetupView` — его показ от
`missing`/`needsRestore` не зависит вовсе. Механизм для них по-прежнему не
найден; версия про фоновый kill процесса озвучена, но ничем не подтверждена —
не гадать дальше, а ловить со стенда на маке так же, как `sars`.

### Найдено и исправлено: SEP-паника `sars` — нули вместо структуры

`RestorePrep.prepare()` создавал `effaceable`/`nvram`/`sep_nvram`/`sep_ssc`
как чистые нули (`truncate`). Сверка с `stage/InfernoData` (эталон с
настоящего устройства с прошлого расследования, `FINDINGS.md`) показала: эти
четыре файла **не полностью нулевые** даже «начисто» — `effaceable` 336
ненулевых байт, `nvram` 188, `sep_nvram` 463, `sep_ssc` 856. (`ctrl_bits` и
`syscfg` — действительно нули, тут `RestorePrep` был прав.) SEP, видимо, не
умеет сам инициализировать это состояние из чистых нулей во время рестора —
и падает `SEP Panic: :sars/sars:` сразу после `RootTicket`, с уходом гостя в
цикл watchdog-перезагрузок.

**Правка**: `app/Resources/SEPTemplates/` — эти четыре файла с реального
устройства, зашиты в бандл (`build.sh`/`build-mac.sh` копируют рядом с
`qemu-data`). `RestorePrep` подставляет их вместо `truncate`-нулей для этих
четырёх имён; `ctrl_bits`/`syscfg`/`root`/`firmware`/`panic_log` остаются
чистыми, как было. **Подтверждено на маке**: `sars` пропала, рестор прошёл
дальше `RootTicket`, дальше NORData, FDRTrustData — не падал на SEP ни разу
за прогон.

### Новая находка, не тронута: `cannot find IOAESAccelerator`

С шаблонами SEP на месте следующий прогон на маке до USB вообще не дошёл:
~60 с тишины (гость 0.1 ядра занятости), затем
`panic(cpu 1 caller 0xfffffff00838c7cc): cannot find IOAESAccelerator`,
watchdog-перезагрузка, и снова ~70+ с тишины без прогресса — закрыто вручную,
не докопано. Раньше по цепочке загрузки, чем `sars` была; в проекте нигде не
упоминалась. Начинать здесь при следующем заходе.

### Заодно сделано (не про SEP, но по ходу)

- **Прошивка копируется в папку приложения** при «Подготовить набор»
  (`RestorePrep.localCopy`), а не читается с флешки/внешнего диска всю
  передачу — меньше зависимости от того, что внешний носитель не отвалится
  на многоминутной операции. Резюме по размеру: недокопированный файл с
  прошлой попытки не считается готовым, а перекачивается заново (было:
  считался готовым, и `IPSW` потом падал на «не архив прошивки»).
- **`UIApplication.isIdleTimerDisabled`** на время рестора и на время
  копирования — экран не гаснет посреди многоминутной операции.
- **На маке не было пункта «Восстановление» в настройках вовсе**
  (`MacSettingsView.Page` — добавлен `.restore`). Не баг сессии, просто
  никогда не добавляли параллельно с iOS-версией.
